# 核心原则

本项目在代码层面遵循以下工程原则。它们是你做技术决策时的"宪法"——无论遇到什么情况，都应该回到这些原则上来。


### 简单至上

最简单的能用的方案就是最好的。不要过度设计，不要为未来不确定的需求写代码。
### 显式优于隐式

代码意图一目了然。避免魔法、隐式约定、过度抽象。读代码应该像读句子。
### 单一职责

一个模块只做一件事，做好一件事。职责清晰的代码才可组合、可测试、可替换。
### 快速失败

不过度设计、过度防御、过度容错。让异常大声暴露而非静默退化。
### 测试驱动

先写测试再写实现。测试即文档，测试即规格。不可测试的代码就是不可维护的代码。


## 测试驱动的节奏

编写代码时遵循以下循环：

```
RED      — 先写一个失败的测试。确认测试确实会失败（不是语法错误，是断言不通过）。
            │
GREEN    — 写最少代码让测试通过。不要多想，不要顺便重构，不要顺手加功能。
            │
REFACTOR — 消除重复、改善命名、提取抽象。保持测试绿。
            │
        重复 ↑
```

### 何时必须 TDD

- 新功能、新模块、核心业务逻辑
- Bug 修复（先写一个捕获 Bug 的测试，再修）

### 何时可跳过

- tiny 任务（改拼写、调配置、修注释）
- 探索性原型（原型验证结束后补测试）
- 纯脚本、一次性迁移工具

### 测试的质量标准

一个测试通过了不代表它是好测试。检查：

- [ ] 测试失败过吗？从没见过它红的测试 = 不知道它到底在测什么
- [ ] 测试名称描述了行为，而不是实现？"用户登录成功返回 token" > "调用 login 返回 200"
- [ ] 一个测试只测一件事？
- [ ] 测试不依赖执行顺序、不依赖外部状态？

### 细则

不过度设计、过度防御和过度容错。让异常大声暴露，而不是静默退化。

- **只做直接需要或明确要求的改动**，不为假设的未来写代码
- **信任内部代码和框架的保证**，不在内部调用链上重复校验类型、非空、边界
- **只在系统边界做校验**（用户输入、外部 API 响应），内部传递的数据不做二次验证
- **不为不可能发生的场景加错误处理、兜底逻辑或 fallback**
- **不为低频调用建 helper、utility 或抽象**，三行重复好过一份烂抽象
- **确定没用的代码直接删掉**，不要 rename 成 `_x`、re-export 或注释留尸


## 原则的优先级

当原则之间发生冲突时，按以下顺序权衡：

1. **安全性** — 数据、资金、权限不出问题
2. **正确性** — 功能按预期工作
3. **可维护性** — 别人（包括三个月后的你）能看懂、改得动
4. **性能** — 在满足前三条的前提下追求效率
5. **简洁** — 代码越短越好，但不是以牺牲前四条为代价

## 原则的使用方式

- agent 在设计方案和编写代码时，应主动对照这些原则自检
- reviewer 会以这些原则作为评审依据，而非个人偏好——做好准备
- 如果某个原则在本项目中经常被打破，应该在团队中讨论：是原则不合适，还是执行有问题

## 不可触碰的底线

- 数据库迁移必须找用户确认后再执行
- 生产环境配置不得硬编码在代码中
- 第三方依赖的新增必须经过评审
