# 测试策略

有行为变化的任务默认采用测试驱动。以下是测试节奏、何时使用、质量标准和交付说明。

## Red / Green / Refactor

```
RED      — 先写一个失败的测试，确认它因为目标行为未实现而失败
GREEN    — 写最少代码让测试通过，不顺手加无关功能
REFACTOR — 在测试保持通过的前提下清理结构、命名和重复
```

## 何时必须先 RED

- Bug 修复：先写能复现 Bug 的失败测试，再修
- 新功能 / 行为变更：先写描述目标行为的测试
- 核心业务逻辑、状态机、权限、安全、数据一致性相关改动
- 重构涉及行为风险时，先补 characterization test 锁住现有行为

## 何时可以不走 RED

- 纯文档、注释、格式化、拼写修正
- 配置、脚手架、一次性脚本等难以自动断言的 tiny 任务
- 探索性原型（原型被保留或产品化前必须补测试）

## 测试质量标准

一个测试通过了不代表它是好测试。检查：

- [ ] 测试失败过吗？从没见过它红的测试 = 不知道它到底在测什么
- [ ] 测试名称描述了行为，而不是实现？"用户登录成功返回 token" > "调用 login 返回 200"
- [ ] 一个测试只测一件事？
- [ ] 测试不依赖执行顺序、不依赖外部状态？

## 交付时说明测试

交付说明必须写清：

- 新增或修改了哪些测试
- 是否见过测试先红后绿；如果没有，说明原因
- 跑了哪些命令和手动验证步骤
- 如果项目没有测试框架、没有测试文件或测试无法运行，说明阻塞原因和替代验证方式
